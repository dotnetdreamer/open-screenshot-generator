# Agent guide: Open Screenshot Generator

Editor for App Store and Play Store screenshots and preview videos. Next.js 15 **static export** (no server, no API routes) plus a Tauri v2 desktop shell running the same bundle. Projects live in IndexedDB. Desktop adds the MCP server, the Claude Code and Codex agents, the embedded-webview AI mode, local AI providers, and loopback OAuth.

## Rules

**Mutating**

1. `handleArtboardsUpdate(next)` is the only door. It repositions boards, writes Dexie, pushes undo. A raw `setArtboards` skips persistence and history. It writes **only** `{ id, name, timestamp, projectData }`, so a new top-level field on `Project` survives until the next keystroke and then vanishes: that is why `ProjectLocalization` is mirrored onto every artboard, and why the cloud-save link lives in its own Dexie table ([src/lib/cloud/links.ts](../src/lib/cloud/links.ts)).
2. Elements render in **two** places: [Artboard.tsx](../src/components/open-screenshot-generator/Artboard.tsx) and `StaticArtboard` in [PreviewDialog.tsx](../src/components/open-screenshot-generator/PreviewDialog.tsx). Miss one and the element vanishes there.
2a. An element with `spanArtboards` is also drawn by the artboards beside it, as a **span copy** ([spanArtboards.ts](../src/lib/spanArtboards.ts)): the strip is the artboards edge to edge in canvas order, gaps left out, tops level. Anything that renders an artboard draws `paintLayers(elements, spill)` with `spill` from `computeSpill` over the same list, never `elements` alone, or a mockup that crosses an edge stops at it on that surface (the canvas, `StaticArtboard` and the video compositor all do; the PNG export rasterizes the canvas, so it gets them). A copy's wrapper carries `data-span-of` and `data-span-source` instead of `data-element-id`, so anything that counts or finds an artboard's own elements still means only those. Whether an element reaches a neighbour is `paintRect`: the box plus the artwork's own transform (an image's skew and tilt, a device's perspective style), its shadow, blur and outline, and the farthest its animation travels; something painting outside its box needs a line there or it is cut off at the seam. In a preview, a spanning element plays to whichever of its artboards is previewing, every copy slides by its source artboard's distance, and a copy's motion counts toward its board's styled MP4 but never the store-safe cut. Absent means cut off: templates, old projects, the AI agent and MCP-built elements leave it unset, and only elements the user adds by hand (the palette, an image dropped on the canvas) start with it on.
3. Text renders at `fontSize / 0.3` px and ignores `element.scale`. Resize text via `fontSize`. The box clips, so every place a **user** edits text content, family, size, weight or line height folds `fitTextBox` ([textFit.ts](../src/lib/textFit.ts)) into the same update. Template data is never re-fitted.
3a. Anything that keeps a text measurement hears that a font has arrived through `onFontsSettled` ([fontsSettled.ts](../src/lib/fontsSettled.ts)), never from `document.fonts` itself. WebKit, which the desktop app runs in, never fires `loadingdone`. It fires `loading` again and again with nothing loading, and `document.fonts.ready` then settles at once, so a listener that measures again on it loops (more than 200 renders in 8 seconds on a blank project). And `document.fonts.check` answers true about three seconds into a load that is still going, so "is this face here yet" is `faceOnItsWay`, not `check`. The probe in `textFit.ts` names every face it measures in (`watchFace`), and `document.fonts.load` for that face is the one signal both engines keep.
4. `ArtboardState.position` is derived and overwritten every update. Authoring it does nothing. So is `backgroundImageSlice`. Both are re-derived by `calculateArtboardPositions`, which also puts a board that has no background picture onto the shared one when `backgroundImageApply` is `all` or `span`. That is what makes a shared background stick: an artboard added later, a dropped preview scene and an agent-made board all join it, and a split re-slices itself after any add, delete, duplicate, reorder or resize, without one of those writers knowing the feature exists.
4a. A board's background **picture** (`backgroundImage`) renders as an `<img>` layer, never as a CSS `background-image`. `exportRaster.ts` explains why: WebKit paints the capture's SVG without waiting for a CSS background to decode, so the PNG would come out without it and nothing would report the loss. Its geometry lives in `artboardBackgroundImageBox`, shared by the canvas, the previews and the video compositor. Give it `max-width: none`, or Tailwind preflight clamps a slice back to one board.
4c. A colour **tint** is applied two different ways on purpose, and the split is about SIZE. An image **layer** gets an SVG filter on its `<img>` (`imageTint` in [elementStyle.ts](../src/lib/elementStyle.ts) + `ImageTintFilter`): one `feColorMatrix` that mixes each channel toward the tint and leaves alpha alone, so `objectFit` and cut-out PNGs are right for free. A **board background** gets a plain scrim div instead. Filtering something board-sized is what WebKit cannot do: measured at dpr 2 while dragging the strength on one 3870x2796 background, per step, **1824ms filtering the picture against 33ms for a div** (the desktop app is a WKWebView, so that is a frozen editor). Two rules follow. The filter id must be derived from the OWNER, never from the tint's values: a value-derived id mints a new `<filter>` and rewrites the `filter:` property every step, which is the 1824ms case; keeping it stable is 363ms. And the filter def must live INSIDE the node being captured, or it is missing from every export. The video compositor mirrors both: `source-atop` for a layer sprite, a board-wide `fillRect` for the background.
4d. An artboard with `creativeAsset` set is App Store header or search art, not a screenshot, and its size is Apple's. Anything that treats every artboard as a screenshot has to skip it, with `isCreativeBoard` or `screenshotBoards` from [creative/specs.ts](../src/lib/creative/specs.ts): the Canvas Size handler, `convertArtboardsToFormat` and `detectArtboardsFormat`, the export's extra App Store sizes and its 01..N numbering, the store upload dialog, `normalizeBackgroundImage` and the span strip in `computeSpill` all do. Its safe area (`safeAreaFor`) is what EVERY device shows, and an iPhone shows far more (`iphoneAreaFor`, measured off App Store Connect's preview): copy goes in the first, screens are sized for the second, and whatever draws the art on a phone crops it with `iphoneCropFor`, never to the safe area. Mixing the two up is issue #46, where designs drawn to fit the safe area came out small on a phone with bare space around them. Name exported art with `creativeFileStems`, never `creativeFileStem` alone: two designs of one kind share a name, and a desktop export into one folder would write the second over the first. Generated creative art adds no CSS filter of its own (no blur, glow or drop shadow): at 3840 to 5244px wide WebKit filters it at full size, and a shadow under each phone froze the add dialog in the desktop project. The phones still carry the small `.device-container` drop shadow every flat frame has, which WebKit got through in the e2e runs. Its type is fitted by MEASURING it, with `fitGlyph` in [creative/typeFit.ts](../src/lib/creative/typeFit.ts), never from an average letter width: a name in capitals sized that way came out a line longer than its box and was cut off. So whatever puts a generated design into the project waits for `lookFacesPending` first (type measured in a fallback face wraps somewhere else once the real one loads), and whatever shows one rebuilds it on `useFontsLoaded`. The app name and the headline are never left out or cut; only the tagline and the line under a headline are. Art already in a project is laid out again with `rebuildCreativeBoard` (the chip's Rebuild design, and on its own when a face that was too slow arrives), never rebuilt behind the user's back when a project opens. It reads a design back off its layers by the part in each id (`cr-<seed>-<kind>-<part>`) and by the layer names on a duplicated artboard, so a design keeps those when it changes.
4e. A size other than the project's own is laid out from the design by `boardsOnDevice` ([deviceSets/sets.ts](../src/lib/deviceSets/sets.ts)): the export's generated sizes, the upload's store sizes, the toolbar's Convert, Every device and Open as a new project all go through it. `convertArtboardsToFormat` is only its `scaled` layout and what an artboard that is not a device's screenshot gets (`takesPart` leaves out header art, Watch artboards and feature graphics). Text is measured, so a caller awaits `facesReady` first. A plan is worked out on the base artboard and applied to each language (`applyPlan`), so every language has the same layout. What a person picks lives on the artboards: `deviceSets[format]` holds the layout and the screenshots added for that device, keyed by element id, so `remapOverrideIds` and `placeArtboard` remap them with the ids and `collectMediaIds` walks them; `deviceSetFormats`, the sets the project exports, is project-level and mirrored onto every artboard on every commit (`mirrorSetFormats` in `calculateArtboardPositions`), so a new artboard joins and deleting the first ones loses nothing; an artboard moving to another project takes the target's. The frame follows the screenshot (`frameFor`): a screenshot added for a device makes the frame that device's whatever its shape (a 7-inch tablet's is as tall as a phone's), while the design's own screenshot keeps a phone frame on a tablet or the Mac unless it is that shape. A frame that cuts off clearly more of its screenshot than the design does (`wrongShape` in `framesOnDevice`: an iPad screenshot in an iPhone or a 10-inch Android tablet) asks for that device's own screenshot, phones included; a phone asks only in those frames. So a project's own device is read from its size (`ownFormatOf`, and `activeDeviceFormat` for the iPad, 10-inch tablet and Mac sizes), never from its frames. The view writes through `onCommit` with a change applied to the project as it is when the write lands (an upload takes a moment), turned down when another document is on the canvas by then (`canvasSerialRef`). Convert and Open as a new project both build with `projectForDevice`, which drops the size and place a language kept for the old artboards and puts each language's device screenshot in its frame. The automatic layout tries every rebuilt layout before it shrinks an artboard to fit; one that cuts text off, or runs text into text or a device further than the design did, does not count (`looksRight`). [deviceSets.test.ts](../tests/unit/deviceSets.test.ts) lays out every bundled template on every device; read a change in a real browser too, since the node tests measure text with a stand-in.
4b. A value the properties form reads out of a board and writes back has to survive `slimArtboard`, which swaps anything oversized for `ELIDED_SRC`. `useDockHost` drops that stand-in on the way home, because a detached panel writing it back would replace the real picture on every board with a string that resolves to nothing.
4f. WebKit paints every capture in software, and its software painter drops the perspective part of a transform. A perspective phone (a perspective preset or `styleType: 'custom'`) or a tilted picture (rotateX/rotateY under the image's `perspective: 1000px`, or its own matrix3d) used to export flat from the Mac app while the canvas showed it tilted. `captureNodeToPng` asks `captureLosesPerspective` once, by painting a turned square through the same SVG path. Where the answer is yes, `preparePerspectiveWarps` captures each element whose plane the perspective bends on its own and flat, warps it on the GPU by its exact 4x4 transform, and puts that picture in its place in the serialized capture ([perspectiveCapture.ts](../src/lib/perspectiveCapture.ts), the maths in [perspectiveWarp.ts](../src/lib/perspectiveWarp.ts)). Chromium keeps the perspective, so nothing changes there. Perspective from an element's own transform or its parent's `perspective` is covered; perspective from further up a `preserve-3d` chain is not. [export-perspective.spec.ts](../tests/e2e/specs/export-perspective.spec.ts) fails on `desktop` and `web-webkit` without the warp.
4g. An artboard with `appIcon` set is the app's icon ([src/lib/appIcon/](../src/lib/appIcon/)), 1024 x 1024. **Paths and platform**

11. Wrap every `public/` asset src in `withBasePath()` from [basePath.ts](../src/lib/basePath.ts) **at render time**. Store paths canonical. `next/image` and `<img>` ignore `basePath` on a string src.
12. All file saves go through [src/lib/desktop.ts](../src/lib/desktop.ts). macOS WKWebView ignores `<a download>`, and WebViews ignore `target="_blank"` (use `openExternal()`).
13. Tauri allows nothing by default. A new command needs a line in `generate_handler![...]`; a new outbound host needs one in [capabilities/default.json](../src-tauri/capabilities/default.json). Missing entries look like network errors but are permission errors. `core:window:default` is **read only**: it answers `availableMonitors` and `outerPosition` but not one setter, and `onCloseRequested` needs `core:window:allow-destroy`, because Tauri prevents the native close whenever a window has a JS close-requested listener and the API's own handler calls `destroy()` to finish it. A new window label needs its own capability file, matched by a glob such as `panel-*`.
14. `isTauri()` is false during SSR and first client render. Gate desktop-only UI on a `mounted` flag too.

A new artboard render site needs one of those two markers or it will go dark. A raw colour that only reads on one ground needs a `dark:` variant.
19. **No em dashes and no en dashes** in anything a user reads. Use a comma, a period, a colon, or "to". No trailing period on short UI copy. Load the `ui-text` skill before writing any, see [Writing comments and user-facing copy](#writing-comments-and-user-facing-copy).

**Input**

20. Canvas interactions are **pointer** events, never mouse events: phones and iPads are supported and a finger fires no `mousedown`. That includes the guards, `onPointerDown={e => e.stopPropagation()}` on a control inside an element, never `onMouseDown`. Anything that must survive a drag needs `touch-action: none` on the thing being dragged, or the browser cancels the gesture to scroll.
21. A finger never hovers and never right-clicks. Hover-only affordances get `data-touch-reveal` (shown outright on a coarse pointer, see globals.css); the context menu also opens on a long press ([OpenScreenshotGeneratorLayout.tsx](../src/components/open-screenshot-generator/OpenScreenshotGeneratorLayout.tsx)); double-click is replayed from a double-tap by [DraggableElement.tsx](../src/components/open-screenshot-generator/elements/DraggableElement.tsx).
22. HTML5 drag and drop (`draggable`, `dataTransfer`) does not fire for touch at all. Palette tiles carry both: the native drag for a mouse, and a long-press drag ([use-touch-drag.tsx](../src/hooks/use-touch-drag.tsx)) for a finger. A new draggable source needs both.
23. The canvas scroll extents are stated in pixels in [CanvasArea.tsx](../src/components/open-screenshot-generator/CanvasArea.tsx), because the board layer is sized by a CSS transform and a transform contributes nothing to a scroll extent. Change how boards are laid out and `contentExtent` has to follow, or the canvas silently stops scrolling to the last board.
24. **A wheel is not a trackpad.** The canvas zooms on a mouse wheel and lets two fingers scroll, told apart by `isMouseWheel` in [CanvasArea.tsx](../src/components/open-screenshot-generator/CanvasArea.tsx) (`deltaMode`, then the legacy `wheelDeltaY` ratio). Ctrl or Cmd with a wheel always zooms, and the listener is registered by hand with `passive: false`, because React attaches wheel listeners passively and a passive listener cannot stop the browser zooming the page.
25. A user-facing switch that more than one place reads goes in [editorPreferences.ts](../src/lib/editorPreferences.ts): one cache, one listener set, live across the app. localStorage alone would leave an already mounted canvas on the old value until reload.

**Writing to storage the user owns**

25a. Two auto savers, and they are not symmetrical. Ours ([cloud/autoSave.ts](../src/lib/cloud/autoSave.ts)) defaults **on** and will create a cloud copy that does not exist yet. The one that writes to a person's own Drive or gists ([account/autoSync.ts](../src/lib/account/autoSync.ts)) defaults **off** and only ever **updates**: a row in the `accountLinks` table is its permission slip, minted only by a manual save or by opening that project from the account, so it can never create folders in somebody's Drive. It also never sweeps orphaned remote blobs, never resolves a conflict (neither provider has a conditional write, so it stops and asks), never clears the session on an expired token, and is held entirely while a live collab session is running. Adding a third destination copies those rules, not the cloud saver's.

**Live editing**

26. A remote change NEVER goes through `handleArtboardsUpdate` (it would republish and fill the author's undo stack with other people's edits); every local write into the CRDT is one transaction tagged `LOCAL_ORIGIN` (or it bounces back forever); nothing large may enter the document (a WebRTC message over ~256KB fails, so media travels as a reference and is fetched from the cloud copy). Full rules in [reference.md](reference.md).
27. The room key lives in the invite's URL **fragment** and is read at module load in [collab/links.ts](../src/lib/collab/links.ts), because Next's router `replaceState`s the fragment away during hydration. Never move that read into a component, and never put the key in a query string or a log.

**Versions**

28. The undo stack never outlives its sitting, and is never written while it is in memory (a hundred project snapshots written as you edit is issue #19 again). The one exception is a project tab that leaves memory while the sitting goes on (it sleeps, closes, or moves to another window): its stack is written once at that moment ([historyStore.ts](../src/lib/tabs/historyStore.ts)) and counts only while the window that wrote it lives, and the window that reads it takes it over, so a reload still starts undo over, in whichever window that is. Crossing a reload is what [versions/store.ts](../src/lib/versions/store.ts) is for, and it is coarse on purpose: five triggers, a thinning curve, and a document that carries media by reference. A restore goes through `handleArtboardsUpdate` like any other edit, after keeping the state it replaces.

**More than one window**

29. The right dock can leave the editor and live on another display, so **the editor window is the only writer**. A detached panel renders a snapshot it was sent and answers clicks with a named intent; the editor replays that intent against the same handler the docked panel calls. A panel window must never write the project, join a live session, run auto save or start the MCP bridge. It renders [RightDockPanels](../src/components/open-screenshot-generator/panels/RightDockPanels.tsx), the same component the dock does, so the two cannot drift.
30. What crosses a window boundary goes through the projection in [protocol.ts](../src/lib/panels/protocol.ts), and that projection is the maintenance cost of the feature: a new PropertiesPanel field it drops will work docked and fail **silently** detached. Media never crosses (elements carry `asset:<id>` and `mediaId`, and IndexedDB is shared by every window on the origin); a `blob:` URL means nothing outside the document that made it.
31. Display geometry is in **physical** pixels, always. A 4K display at 150% next to a 1080p at 100% has no shared logical origin, so a position computed in logical units on one lands somewhere else on the other.

**Screenshot intake**

32. An uploaded screenshot is stored **once** and travels as `asset:<id>` ([intakeAssets.ts](../src/lib/intake/intakeAssets.ts)). The results deck renders the same shots inside a dozen templates at once, and `getMediaUrl` caches one object URL per id, so every card shares one decoded image. Pass a `data:` URL around instead and each card decodes its own copy of a 2796px PNG.
33. Ranking and filling are **pure and offline**: [templateIndex.ts](../src/lib/intake/templateIndex.ts) derives its index from `projectData` (never a hand-authored tag file, which `gen:ai-catalog` would then have to track), and [autoFill.ts](../src/lib/intake/autoFill.ts) is a pure transform over a deep copy, so a preview can be rebuilt on every keystroke. `fillTemplate` keeps the template's own `id` because `handleSelectTemplate` reports it to analytics.
34. Duplicate screenshots are matched on the analysis **fingerprint** plus dimensions plus byte length, never on byte length alone: two different screens of one app routinely compress to the same size, and the user's set silently arrives short.
35. Every device frame in the catalog ships with placeholder art, so "is this frame empty" is never `!screenshotSrc`. A shipped placeholder is a public path; the user's own content is `asset:`, `data:` or `blob:`.
36. A card that would overspend the WebGL budget renders **flattened** (`flattenBoard3d`), never as the shipped preview PNG: the whole point of the deck is that the boards hold the user's screenshots.

39a. Installing an update ends the process without any window's close hook, so `updater.rs` first asks every editor window to write its edits (`abs-update-flush`, answered with `abs_update_flushed`) and calls the install off when one cannot. Anything that must be written before a window goes away belongs in `beforeWindowCloseRef`, which both the close hook and that handshake run; a writer that only listens for the close is lost on every update. Child processes the app starts die in `stop_agents` there too, beside `RunEvent::Exit`.
39b. What a build does about updates is decided in Rust (`detect` in `updater.rs`), never by the page: an installer build installs, the portable exe (no bundle-type mark) only links to the download, and the MSIX (package identity) and the Mac App Store build (sandbox) never check. The update server and the public key reach a build only through the overlay CI writes (`scripts/updates/configure-build.mjs`), so a local build and a fork have no updater; do not put either value in `tauri.conf.json`. The page can never call the updater plugin itself: no capability grants it, and the four `abs_update_*` commands answer `main` only.

**Project tabs**

40. Only the active tab's project is on the canvas. Leaving a tab parks its document and undo stack by reference in the parking lot ([parking.ts](../src/lib/tabs/parking.ts)), and coming back restores them without a read. `putProjectOnCanvas` is where the outgoing project is parked, so anything that puts a document on the canvas keeps going through it. Per-project canvas state that has to survive a switch goes into `ParkedProject` (memory only) or `TabView` (kept in the session) in the same commit, or it leaks from one tab into the next.
41. A project gets its tab from `activeProjectId` changing, in one effect, which is why no open path knows tabs exist: do not add tab bookkeeping to one. A template opened from the gallery is a preview (`previewProjectIdRef`) until its first commit reaches `scheduleProjectSave`, and the next project opened from that tab takes its place.
42. A project that is not on the canvas changes only through `editTabInBackground` (or `editProjectAnywhere`): it writes the row, pushes onto that project's own undo stack, and writes its pending "Before this session" version. A bare `db.projects.put` of a parked project is undone the moment its tab opens, because the parked copy goes back on the canvas.
43. A parked tab stays in memory, never trimmed, for an hour after it was left (`DEFAULT_PARKING_BUDGET`), or until the lot passes 256MB of snapshots or twenty tabs, when the tabs left longest ago go first (the bytes are for projects heavy with inline media: the macOS webview killed the page at about 500MB, issue #19). Then it sleeps: its project is already in IndexedDB, `onSleep` writes its undo stack (rule 28), and opening it reads both back. The tab session in storage is the list and each tab's view, never a document or a history; the active tab's view is read as the session is written (`readView`), because a reload never leaves the active tab.
44. One window writes a project. Each tab holds a Web Lock for its project ([projectLocks.ts](../src/lib/tabs/projectLocks.ts)), and the lock is taken BEFORE a project is opened or written, on every path: the loader, `loadProjectFromData` (which throws `ProjectOpenElsewhereError`), and `importBundle`'s `beforeWrite` for opens that write the row first (account, cloud). A tab leaving for another window writes its project and undo stack before it lets go of the lock (`letTabGo`), and the window taking it waits for the lock (`HAND_OVER_WAIT_MS`). A move between projects holds both locks from its first read to its last write (`withProjectsHeld`), and whatever lets a project go (closing its tab, `letTabGo`, a `hand-over`) waits for the moves under way; a lock goes only once nothing in the window has the project (`letGoIfUnused`). A window a tab was moved into carries `?tabwindow=<key>`, keeps its tab session under that key, and stays out of what only `main` runs: the MCP bridge, the coding agents, detached panels (`useDockHost` with `enabled: false`: a panel window adopts any host that announces itself), the native menu's About. A Tauri `listen()` with no target hears events emitted to every window, which is why a main-only listener also needs the Rust-side check (`abs_mcp_bridge_nonce` refuses any other label).
45. Layers moving between projects go through [transfer.ts](../src/lib/tabs/transfer.ts): fresh ids, groups kept together, translations carried only into languages the target has, elements rewritten in the target's base language when it differs (`rebaseLanguages`) with every language drawing as it did (a property a language never set is stored as null in its override, which projection reads as unset), and a per-language position moved with its element. The source is the project captured before the first `await`, written through `editProjectAnywhere`; by the time the target's write lands the canvas can show another tab, one that may share board ids with the source. An artboard moving to another project takes that project's `localization` and keeps a shared background picture to itself. The File menu owns Ctrl+W (Close Tab), Ctrl+T and Ctrl+Shift+T, and Close Window is Ctrl+Shift+W ([settings.rs](../src-tauri/src/settings.rs)).
46. The layer clipboard is one for the whole app ([elementClipboard.ts](../src/lib/elementClipboard.ts)), so a copy in one tab, project or window is what a paste in any other reads. It lives in localStorage with a copy in memory, read again on focus and at paste time because a webview can miss the `storage` event, and it holds a transfer that a paste lands through `placeElements`: rule 45 holds for a paste as it does for Copy to tab. Never move it back into React state or a context, or other windows stop seeing what this one copied. Media and imported fonts belong to the device, not to a project. A layer rewritten in another base language stores the size its text fits at, measured in that language's face, so a paste, Move or Copy to tab and Move or Copy artboard to tab put every face the layers draw in on the page first (`whenFacesLoaded` in [transferFonts.ts](../src/lib/tabs/transferFonts.ts)), a font imported in another window after this one started included, and a built-in family whose stylesheet has not arrived (until it does, `document.fonts.check` calls a face the page has never heard of ready, so `whenBuiltInFacesDeclared` comes first). Measured before, the fallback's size is stored for good, which no refit afterwards repairs. The layers stay editable while their faces load, and a language of their project can be set to draw in another face (`autoFont`, through an agent's `add_locales`) without any layer changing, so a move picks them again after each wait and waits again while the faces they need now are not in, comparing faces rather than layers (`pickWithFacesIn`). It takes them out of their project only as they went (`stillHolds`, `sameDocument` for an artboard): one edited meanwhile stays where it is.
47. Closing a tab that has changes asks first (`confirmTabClose`, which Settings can turn off), and a bulk close closes exactly the tabs it asked about. Changes means the project took a commit of any kind in this sitting: `openedSnapshotRef` (or `ParkedProject.openedSnapshot`, or `sleptWithChangesRef` for a tab asleep) is gone, never a history row's icon, since a restored version and an applied template use the Open icon. A change from a live session counts too (`applyRemoteArtboards` calls `noteVersionCheckpoint`), unless the room handed back the document the canvas already shows (`sameDocument`). A close that also leaves a live session asks only about the session. A tab dragged out of its strip and let go over another editor window moves there ([tabDrag.ts](../src/lib/tabs/tabDrag.ts)): only the dragging window knows where the pointer is, so as the drag starts the others say where they are (`tab-drag` `start`, answered by `tab-drag-window`), and the dragging window decides where the tab lands from the RELEASE position, never from the last frame. The web compares CSS pixels (a pointer event's `screenX` against `window.screenX` and `outerWidth`) and decides inside the release, which a popup needs; the desktop compares physical ones (`cursorPosition` against `outerPosition` and `outerSize`, rule 31). A tab that leaves for another window stops every open of its project still under way here and waits for it (`stopOpening` in `letTabGo`): its own read, `loadProjectFromData`, and an open from the account or the cloud from the moment it claims the project, whose row write goes through that open (`guardRowWrite`) and is refused once it is stopped. Left to finish, an open would write the project or put it on this canvas after the other window took it. From the same moment, anything here that asks for the project's lock is turned down (`startHandOver`), though the lock stays held for the last writes: let through, an open of it from Recent projects found the lock held here and opened, and both windows saved it. Closing a tab stops only its own read. Anything an open does after the project is on the canvas, such as writing the address bar, belongs in the same step as the canvas, not after an `await`.

**Growth (App Store numbers)**

48. A feed that reports a day REPLACES its own fields on that day ([records.ts](../src/lib/growth/records.ts) `mergeFeed`, `FEED_FIELDS`), never adds to them: Apple re-issues past days, and a retry or an overlapping analytics instance must not double a number. Day rows are read, merged and written inside `withDayLock` in [sync.ts](../src/lib/growth/sync.ts), a Web Lock, because Sales and Trends, the analytics import and a sync in another editor window all write the same rows. A Sales and Trends day is recorded as fetched only in the flush that writes its rows: recorded first, a stopped run leaves a fetched day with no rows, which no sync fetches again and `zeroFill` turns into a zero. And anything that clears an app's data clears that record too (`clearApp`).
49. Every window ends at `completeThrough`, the newest day EVERY feed has reported, never at the newest day of any feed: Sales and Trends lands a day before App Analytics, and a window ending on that day compares 13 days of impressions with 14 and reads as a fall. Conversion is only computed over days that have both impressions and downloads. A figure is compared with an earlier period only when its feed's history reaches back over all of that period (`covers` with `feedStarts` in [metrics.ts](../src/lib/growth/metrics.ts)): the first sync brings a year of Sales and Trends and less App Analytics, and a period half before the data reads as a leap. Never test coverage by counting days with rows: App Analytics sends no rows for a day nobody saw the app, so a small app would never be compared. For the same reason each analytics file answers for its own days, rows or not (`instanceDays` in sync.ts): every date it has rows for (a small app's day is often auto-updates only), a snapshot's whole span up to its processing date, and a daily file's day before its processing date with its recent days. Those are zeros wherever nothing else is stored (`onlyIfMissing`). A day between two files belongs to no file and stays missing, never a zero: Apple deletes a file 35 days after making it, and developers report daily files that skip a day. `dayValues` takes the downloads of a day no file covered from Sales and Trends, which counts them another way: covered days left to it read 51 new downloads beside a source breakdown adding up to 44, and zeros made up for deleted files dropped 9 downloads Sales and Trends had seen. Missing days, or a report whose snapshot has not been read, ask Apple for a new `ONE_TIME_SNAPSHOT` (`snapshotDue`), at most once in 31 days, since Apple answers 409 sooner. The digest names the missing days that fall in its two windows (`missingAnalyticsNotes` in digest.ts), so the agent's `get_store_overview` and the Ask tab do not read a gap in impressions as a drop. A sync skips a file it has read, so when the import starts storing something new, raise `ANALYTICS_IMPORT_VERSION`, and files read under an older version are read again. A report owes only the days after the app's first number; a period that starts earlier says where the numbers start (`numbersFrom`). Product page views are the `Product page` rows of the engagement report only (`isProductPage`): Apple also counts views of the privacy, version history, developer and media pages, and the downloads half of the rate is product page only.
50. A screenshots (or listing) event is measured from the release of the version it was uploaded to (`liveDateFor` in [impact.ts](../src/lib/growth/impact.ts)), because the store shows nothing new before then; the publish dialog records that version (`recordScreenshotUpload`). No verdict before `MIN_DAYS_AFTER` (7) days; until the 14 are in a change needs `EARLY_CONFIDENT` (99%), since the window is looked at again every day, and `CONFIDENT` (90%) after (`confidenceBar`). The UI never prints a confidence above 99%. It is a before and after comparison, not a controlled test, so no copy says the screenshots caused a change ("up 19% since your new screenshots went live", never "lifted"), and every result names what else could have moved the numbers in its windows (`impact.others`): the other timeline events, and any likely App Store feature its browse impressions show (`likelyFeatures`, the same spike rule as the feature card, `isFeatureSpike`).
51. The agent's store tools (`get_store_overview` and the six beside it, `list_store_keywords` among them) are read only and refused to every caller but the app's own agents unless the user switched sharing on (`mayReadStoreData`): the numbers include sales. Review text reaches a model only fenced and labelled as written by the public. Replies and listing changes are sent from Growth by a person, never by a tool. Growth shows real apps only: with none (the web build, no key) every screen draws empty and each action is a `Gated` button with the reason (`blocked` on the view). Its writing jobs go through `runGrowthPrompt` in [ai.ts](../src/lib/growth/ai.ts): the Claude Code or Codex the user is signed in to (`abs_claude_prompt`, `abs_codex_prompt`: one prompt, no tools, no MCP, no conversation saved, from any editor window, `main` or `editor-*`, never a panel or assistant window) or the AI panel's provider, as the `aiWriter` setting says. Each prompt carries a page-made id, and an aborted signal calls `abs_*_prompt_stop` with it, which kills that process: letting go of the promise alone left the CLI running and holding one of its three slots. A window that closes or starts loading a page takes its own prompts with it (`stop_window_prompts`, from lib.rs's run loop and `on_page_load`); closing `main` ends only main's agent and prompts, since a tab window can outlive it.
52. Proceeds stay in the currency Apple paid them in. `primaryCurrency` picks the headline currency by rough value (`ROUGH_PER_USD`), and nothing adds two currencies together. Two periods side by side share ONE currency, `proceedsCurrency(current, previous)`, passed to `metricValue`: each picking its own printed one period's yen under the other's dollar sign, with a change of +1,400%.
53. Growth syncs on its own when `dueForAutoSync` ([autoSync.ts](../src/lib/growth/autoSync.ts)) says so, never on a once-per-session flag: the Growth view checks when it is shown and every ten minutes while it shows, and the background monitor ([monitor.ts](../src/lib/growth/monitor.ts), run by `useGrowthMonitor` in the main editor window only, paused while Growth is the view on screen) checks every 15 minutes. Both note their attempts in the same book, so they never start one app twice and a failing sync is retried an hour later, not on every render. The monitor only syncs apps already synced in Growth (they have a `sync:last:` row), and the first look at an app records its insights as seen rather than announcing every card. Setup's saves (a key, the vendor number, the reports address, cleared ones too) leave every app of that store owing a sync (`owed` in GrowthWorkspace.tsx), kept per app until a sync that began after the change: the app on screen syncs at once, or when the sync under way ends, and any other app when it shows next. A debt dropped when the picker moved on left an app at "Add your vendor number" for hours.
54. Anything a Growth screen holds that must outlive a section change lives outside the screen: the view mounts a fresh screen per section (`key` on its `<main>`). Listing edits are in [listingDrafts.ts](../src/lib/growth/listingDrafts.ts), stored per app in the growth database and rebased on the listing as it is now (`rebaseChanges`); in component state, a click on Reviews threw them away. Change them with a functional update against the current list, never a snapshot taken before an await: the fields stay editable while Apply waits for Apple, and `withoutApplied` removes only the changes whose text went out unchanged. The same goes for work under way: the Listing action running and its last message (`job`, `note`) and the report summaries being written ([reportSummaries.ts](../src/lib/growth/reportSummaries.ts)) live outside the screen too, so a screen mounted mid-way shows them instead of offering to start them again. Work whose answer only the screen holds (a suggested reply, a translation in the Reviews) is stopped when the screen goes, with its AbortSignal.
55. Every Growth request to App Store Connect goes through `send` in [asc.ts](../src/lib/growth/asc.ts), which gives a 401 one more try with a freshly minted token, and a 429 or 5xx one more try after a pause, for reads only (a reply or a listing change that hit a server error may have gone through). The upload's `apiRequest` in [appStoreConnect.ts](../src/lib/publish/appStoreConnect.ts) retries a 401 the same way. In November 2026 a live sync got one 401 for a valid key in the middle of a burst, and a replay got one 500, and a 401 counts as a bad key and stops its feed. A refused key never stops the ratings feed, which reads Apple's public lookup without one.
56. App Store Connect tokens are dated by Apple's clock, not the computer's: both request paths pass every answer to `noteAppleClock`, which reads its Date header, and `bearerToken` mints on that time with `iat` a minute back. Measured live (November 2026, `GET /v1/apps`): Apple refuses a token whose `iat` is more than about 120 seconds ahead of its clock, or whose `exp` is more than 1200 seconds ahead; an `iat` ten minutes back is fine. The PC the feature was tested on ran 96 seconds fast with its time service stopped, about 24 seconds from that line, so never date a token from `Date.now()` alone.
57. A .p8 is imported as Apple ships it and, when WebCrypto refuses it, once more without the curve its ECPrivateKey repeats (`withoutEcParameters` in [jwt.ts](../src/lib/publish/jwt.ts)). WebKit refuses any EC PKCS#8 key carrying that optional `[0] parameters` field with a DataError, and every key from App Store Connect carries it, so without the retry the macOS app could neither upload nor sync (seen November 2026). Node's `generateKeyPairSync` never writes the field, so a spec signs with a key rebuilt in Apple's shape, or WebKit runs the happy path only.
58. The activity bar switches views ([ActivityBar.tsx](../src/components/open-screenshot-generator/ActivityBar.tsx)). The editor stays mounted under every other view, `inert` while one is in front, and its keyboard handlers stand down through `activityRef`, or Delete and Cmd+Z in Growth would change a canvas nobody can see. A view is mounted on its first visit and kept, so it is as it was left. A new view is one entry in `ACTIVITIES` and one branch in the layout (`belowActions` draws it under Discover, as Website is); a button that opens something instead (Discover, Account, Settings, About) is an `ActivityAction`. Every button shows its short `name` under the icon (a two word name takes two lines); the longer `label` is the tooltip and the accessible name, which tests find the buttons by, so it starts with the name. A new name must fit a 4rem button at 11px, bold included, as the open view's name is drawn. The editor and every view start where the bar ends through `BAR_INSET`, never a width of their own. Below `md` there is no bar, so those four stay in the editor's sidebar for phones.

**The Growth browser and the Ask AI assistant**

58a. The Growth browser ([growth_browser.rs](../src-tauri/src/growth_browser.rs)) is a child webview of the editor window (`Window::add_child`, which is why `tauri` has the `unstable` feature); Linux packs a window's webviews into a GTK box, so there it gets a window of its own. Its page is a third-party site that can call **no command**: no capability names it, and Tauri refuses every app and plugin command from a remote origin that no capability covers. Never add one. One door stays open in Tauri 2: any webview may fetch a queued Channel message by its number (`plugin:__TAURI_CHANNEL__|fetch` skips the ACL check), and Channel messages over 8 KB (1 KB raw) wait in a queue all webviews share. So the app sends nothing over a `tauri::ipc::Channel`, and the Rust test `the_app_sends_nothing_over_a_tauri_channel` fails on one: it reads the Rust tokens of every file under `src-tauri/src`, and no identifier there may contain `Channel` but updater.rs's own `ReleaseChannel`, so spacing, an alias made in another file, a macro or `r#Channel` cannot hide one; command replies and events reach the editor directly, never through that queue. The editor drives the page through `abs_growth_browser_run`, which runs one driver command with `eval_with_callback`. The driver ([driver.ts](../src/lib/growth/setup/driver.ts), bundled to `src-tauri/growth-browser/driver.js` and `include_str!`'d) answers with a **string** only: wry hands an object to `NSJSONSerialization` and unwraps, so an answer it cannot write ends the app. Rust reports page loads, titles, blocked sites and key files with `emit_to` the window that opened the browser, and to no other.
58b. The browser's own page loads reach lib.rs's `on_page_load` as the editor window's (its window label is the editor's), so that hook returns early for `growth_browser::LABEL`; without the early return, every App Store Connect navigation would stop the window's Claude Code and Codex prompts. A new per-window hook goes after it. The commands answer the window's own page only (`webview.label() == window.label()`). On macOS the title bar lies over the top of the page's webview and WebKit starts the page 32 points lower, while a child webview is placed from the webview's top: `Bounds::in_window` adds the gap (the webview's height less `viewport`, the page's own height), which is zero on the other platforms and in full screen.
58c. What the browser may load is decided in Rust: `may_open` (the consoles, for the assistant and the address bar) and `may_load` (Apple's and Google's domains, for every frame, because wry asks about frames too). A debug build also opens `http://127.0.0.1`, for tests, never `localhost`, whose dev origin Tauri treats as the app's own. A download is refused unless it is a .p8 or a service account JSON, which Rust reads from the cache, checks, sends to the owner window and deletes. macOS reports a finished download by its address alone, so one download per address runs at a time (`Downloads`): a second one from the same address, as a double click starts, is turned away, and WebKit's failure report for it is matched to the turning away rather than to the download still running. When a download ends, and when a new browser opens, every file in the cache that no download is writing is deleted.
58d. The assistant ([assistant.ts](../src/lib/growth/setup/assistant.ts)) sends one prompt per turn through `runAssistantTurn` (rule 51's `runGrowthPrompt`: no tools). Its answer names actions, and the page runs them under [policy.ts](../src/lib/growth/setup/policy.ts) whatever the model says. A control or a list option that deletes, revokes, removes or turns something off is never pressed or chosen, nor is anything but Cancel in a dialog whose title says so. One that creates, sends, saves, invites or enables, a bare OK or Yes, or one the model marks `changes` waits for the user's yes, whatever its role: a link can save as well as a button can. That includes a control that only opens the form where the change is made ("Generate API Key" before the dialog's "Generate"): a label cannot say which of the two it does. A list option is judged by the text the list really has (`pick` with `preview`) before it is chosen. The driver checks again in the moment it acts: it presses, types or chooses only while everything the policy read still holds (`expect`): the same page (a driver's numbers start again on every page) at the same address (a single-page console moves without a new page), the control's name, role and link, the title of the dialog around it, and for a list the value the option sets. It checks once more after every step of the action, because the page's own handlers run between them: a mousedown can rename the button and a focus can turn a text box into a password box, so the click itself, or the first letter, happens only if nothing changed. So a page that relabels a control, retitles its dialog or changes an option's value after the user said yes gets nothing done. It also does nothing at all while a sign-in form shows, which a click earlier in the same answer can bring up; that check and the outline's use the same test for a secret box. It never reads or types into a password, code or other private box (`secretOf`), and it tells elements apart by tag name, never `instanceof`: a frame from the same site has its own `HTMLInputElement`, so `instanceof` passes a password box in a frame off as a text box. A value is saved only if it appeared, standing on its own and not inside a longer number, on a page read, in something the page copied, in a key file's name or in a user message (`seenIn`). Private keys never reach a model: downloads, picked files and keys pasted into the chat all go to `addKeyFile`, which tells the model names and emails only, and a key shown as page text or typed into a message is hidden by `redactSecrets` ([secrets.ts](../src/lib/growth/setup/secrets.ts)) in the driver and again in `turnPrompt`. Hide before you cut: text cut to length first can leave a piece of key too short to recognise, so the driver's `squash` and the transcript both redact the whole text, then shorten it. A page can also split a key into short elements, so the driver looks for keys in each outline line as the page renders it, glued together, and for a key's BEGIN and END lines with every space taken out; a line with key text is hidden whole, and so are the lines of key text between BEGIN and END. The assistant takes at most `MAX_STEPS` prompts before the user does something (a message, an answer, a key file, Done); a refresh that ends or a key file the browser catches wakes it too and counts against the same allowance. The conversation lives outside the screen, as rule 54 asks.
58e. The browser is a native view on top of the page, so nothing the page draws can cover it. `GrowthBrowserPane` hides it while a Radix popper or dialog intersects its box (`OVERLAYS`), and the toasts move to the top left while it shows (`html[data-growth-browser]`); a new kind of overlay that can open over the pane goes into `OVERLAYS`. Passkeys don't work in it: WebKit gives an app's WKWebView WebAuthn only with Apple's browser entitlement or for the app's own associated domains, and this app has neither for Apple's or Google's sign-in, whatever the user agent says. Sign-in pages show the email and password hint, and the instructions tell the model the same. Below 1024 pixels the chat and the browser take turns: the chat is hidden, never unmounted, while the browser side shows, so the draft, the scroll and the file picker stay, and a key file request brings the chat side up. The unsent draft also outlives the screen (`unsent` in GrowthAssistantChat.tsx). The desktop e2e harness stands a frame in for the browser and runs the real driver in it (`growthPages`, `growthDriver` in [tauri-runtime.ts](../tests/e2e/fixtures/tauri-runtime.ts)). [growth-browser-driver.spec.ts](../tests/e2e/specs/growth-browser-driver.spec.ts) runs the driver alone in Chromium (WebView2) and WebKit, on pages that try what it must refuse: a password in a frame, a code box with no autocomplete, a key shown as text, a button renamed after the yes, a sign-in form that a click brings up.

**Growth's ratings and reviews**

58f. The stores keep no ratings history: Apple's lookup and both stores' pages say what a rating is now. Growth keeps its own, a `ratingDays` row per app and day (`RatingDay`, Dexie version 2 of the growth database), and every writer goes through `recordRatings` in [ratingHistory.ts](../src/lib/growth/ratingHistory.ts), which merges in one transaction, so the lookup, the store page and a competitors check in another window each add their fields to the same day (`mergePoint`). New ratings are the difference between two readings of the SAME country (`stepsOf`), never between totals, because a refresh between full sweeps reads one country and a total would jump with every country it adds. Stars from a Google Play page at both ends give exact per-star counts (Apple shares no stars, see 58h). Without them the new ratings' sum is average times count now less before, and Apple rounds the average to five decimals, so the sum can be off by 0.000005 times both counts; when that is more than a quarter of the new count (many ratings, few new ones) `newSum` is null and the screen says the average cannot be worked out rather than show one. A count that falls below half is Apple's reset, a smaller fall is ratings taken away and counts as none. On Google Play "all countries" is the `ZZ` row of the report files (averages, no counts), never a sum of countries. The `ratings` table stays the source of what a rating is now for every other screen; the history only adds. "Remove the data" keeps the history and the review marks, as it keeps events the user added: no refresh can bring them back.
58g. Every refresh writes reviews whole (`writeReviews` is a bulkPut), so what the user adds to a review (tags, Done) lives in the `reviewMarks` table, and a rating change a refresh notices is carried over by `carryReviewHistory` ([reviewInbox.ts](../src/lib/growth/reviewInbox.ts)) in EVERY writer of fetched reviews: `syncReviews` in sync.ts, the Reviews API and the monthly files in playSync.ts. A new writer that skips it erases "Changed from 2 to 4 stars after your reply". The state is derived, never stored: a reply makes a review Replied even when it was marked Done. The inbox's keys (J, K, R, E, X, /) listen only while the Reviews screen is mounted and Growth is the view on screen, and stand down while the user types or a menu, popover or dialog is open (`typingOrMenu`). A card action must not contain the word "Reply": the specs find the Reply button by name, and a second button with "reply" in its name made those locators ambiguous.
58h. Reading other apps, measured 2026-11-14 (details in the files): Apple's customer reviews feed (`itunes.apple.com/<cc>/rss/customerreviews/...`, [publicReviews.ts](../src/lib/growth/publicReviews.ts)) answers any web page, 50 reviews a page, 10 pages, and waits its turn in `lookupTurn` with the lookup, since it is the same server. The App Store web page has the stars (`serialized-server-data`, `$kind` "Ratings", `ratingCounts` five first), and curl gets it, but apps.apple.com answers the desktop app's own HTTP client (tauri-plugin-http) with 403 for app pages, with or without a browser User-Agent, while its robots.txt and the reviews feed answer that client with 200. Growth does not read it, and nothing should try to get past that refusal. A Google Play page has the stars at `[51][1]`, one star first, and 20 reviews in a block of their own (`readPlayReviews`), which the competitors check keeps since it reads the page anyway. Unfollowing an app forgets its reviews and its ratings history with its snapshots (`forgetUnfollowed`).
58i. The review summary's AI only sorts: it gets the reviews with short ids and answers with themes and ids ([reviewSummary.ts](../src/lib/growth/reviewSummary.ts)). Counts, shares, stars and quotes are worked out from the ids, an id the list did not have is dropped, and a theme left with none goes. Never print a number the AI wrote. The job runs outside the screen (rule 54), keyed by app and scope, and Stop aborts its signal, which ends the CLI (rule 51). Summaries on a schedule ([reviewSchedule.ts](../src/lib/growth/reviewSchedule.ts), `reviews:summary-every:<appId>`) are written by the background monitor after its pass, in the main window only and only with an AI ready; a failed one waits a day before it is tried again, so a pass every 15 minutes never asks the AI over and over.
58j. New reviews are looked for at the end of every refresh, on both stores (`noteNewReviews` in [reviewAlerts.ts](../src/lib/growth/reviewAlerts.ts)), so whichever window refreshed, a review is told about once. The first look at an app records what is there and tells about nothing, and a review older than 14 days is never news (the monthly Google Play files bring old reviews late). The in-app message waits in `reviews:untold:<appId>` for the background monitor, and the Growth view clears it for the app on screen. Slack is posted to from the desktop app only (`bridgeFetch`: Slack sends no CORS header), and only to an address on hooks.slack.com, with what reviewers wrote escaped for Slack's markup.
58k. Star charts use the `--growth-star-1` to `5` scale and tags the `--growth-tag-1` to `8` slots in [globals.css](../src/app/globals.css), checked with the dataviz validator against the card in both themes. The three-star middle is a neutral grey under 3:1, so every chart of stars has a legend and its counts as text. The e2e helper `putGrowthRows` makes the growth database at IndexedDB version 30 (Dexie 3) when it does not exist yet; a spec that opens it with an explicit version has to ask for 30, or it fails with a VersionError once the app made it.

58p. App health ([health.ts](../src/lib/growth/health.ts), fetched by [healthSync.ts](../src/lib/growth/healthSync.ts), drawn by [GrowthHealth.tsx](../src/components/open-screenshot-generator/growth/GrowthHealth.tsx)) is a feed of its own, `health`, on both stores, run before the ratings sweep, whose line stays the one that says a sync is over. It is kept in one meta row per app (`health:<appId>`), never a Dexie table, so the e2e helper's database version stays 30 (58k). App Store: the reports named exactly "App Crashes" and "App Sessions Standard" from the App Analytics requests the analytics feed keeps (never "Detailed", "Context" or "App Crashes Expanded"; names as Ludo Wala's request listed them on 2026-11-16), read file by file (`health:done:<appId>`) with the analytics day rule (`instanceDays`, moved to [reportDays.ts](../src/lib/growth/reportDays.ts) so both readers share it). A file REPLACES its own fields on the days it answers for (`mergeHealth`), like rule 48. Apple sends no crash file for a day under its five-people line: the account's four apps had sessions files and not one crash file. So a crash rate counts only days a crash file answered for (`crashDays`), says how many of the days with sessions those were (`coveredDays`), and is compared only at `MIN_CRASH_COVERAGE` (three in four) or more; "no crash numbers" never reads as "no crashes". Freezes on the App Store are Xcode's hang rate (`GET /v1/apps/{id}/perfPowerMetrics?filter[metricType]=HANG`, Accept `application/vnd.apple.xcode-metrics+json`): read by category, never by metric name, with Apple's own unit, since only Apple's documented launch example has been seen; every app on the account answered 200 with no data. Google Play: Android vitals from the Play Developer Reporting API (`userPerceivedCrashRate`, `userPerceivedAnrRate` and their `distinctUsers`), daily in America/Los_Angeles days, each measure asked twice, for every build and by `versionCode`, and averaged over days by users the way Google's own 7 and 28 day figures are. Measured on Ludo Wala on 2026-11-16: rates come as shares with four decimals ("0.0185" is the 1.85% Play Console shows), `distinctUsers` in steps of ten, and the build as `stringValue` (`int64Value` is read too). Vitals count builds only. A build's version comes from the reviews, which carry both: the Reviews API's `appVersionCode` and the report file's "App Version Code" are kept as `appBuild` (reviews stored before that get it from their month file, read again once under `play:review-builds:<appId>`; only the build is filled in). After the reviews, a Play Console release name gives the version only when Play Console made the name itself ("138 (1.3.8)") or it is a version number. Most release names are typed ("New help form" is Ludo Wala's build 205, version 1.4.65): such a name shows beside the version, never as it, and a build nobody reviewed is "Build 205". Release names come from the tracks, read through an edit that is deleted again (`fetchPlayTracks`), and are stored as `releaseNames`. A 403 with reason SERVICE_DISABLED (measured 2026-11-16 on the test key) is `needs-setup` with a `link` to the `activationUrl` in its details, and only a console.developers.google.com or console.cloud.google.com address is ever offered. The health chart uses the ratings chart's buckets (`bucketsIn`), margins, axis width and `syncId`, and the review strip is placed by the same point or band positions, so a day lines up with the day above it; a chosen version shades its days on every chart (`ChartBand`). On a line chart each bucket is a point, so a shade is drawn to the neighbouring buckets and trimmed back by half a bucket (`BandArea.trim`), which gives one day a day's width as on the bar charts; a line chart of one bucket (the last 7 days by month) puts it on one point in the middle, so its shade is the whole plot (no x1 or x2, which Recharts fills with the plot when a shape is given). A bucket holding more than one release says how many on its line ("2 versions") instead of naming one of them. The versions table is newest first by version number (App Store) and build number (Google Play), the numbers each store makes go up, never by the first day a version was seen. Its Dates say which kind they are: **Released** is the day of a release event on the timeline, **Seen** the first and last day the store counted people using it (or, without numbers, Growth saw it on sale or reviews named it). A version's days on the charts run from its release to the day before the next one came out, else its seen days, and an App Store review counts for the version that was newest on its day. Ratings with nothing to show still shows the health status and its setup button (`HealthStatus`). Each store keeps its own unit (per 1,000 sessions, a share of users), never one turned into the other. A finding (`healthFinding`) needs two versions with steady numbers (200 sessions or 200 user days, and the coverage above) and a rise or fall of 1.5 times and a minimum step, or on Google Play a crossing of Google's line (1.09%, 0.47%); its words say what moved with a version, never that the version caused it, as rule 50 says for screenshots.

**Growth's Keywords**

58l. Ranks come from `itunes.apple.com/search` (`searchUrl` in [keywords.ts](../src/lib/growth/keywords.ts)): Apple's documented Search API, `entity=software` and `limit=200`, fetched with `cache: 'no-store'` and paced by `lookupTurn` with the lookup and the reviews feed, since they are one service with one 20-a-minute budget. It answers any web page, so Keywords works in the web build. Measured 2026-11-15 against apps.apple.com's search page, 18 searches in 8 countries: the same first app in all 18, 108 of the page's first 180 apps at the same place, 170 within two, the worst 30 off (details in the file header). That is the web App Store; the App Store app was not compared, so no copy may promise more than that. Three sources are not used, on purpose: apps.apple.com (403 for the desktop app's client, rule 58h), Apple's typed suggestions at MZSearchHints (undocumented, no CORS, and it needs a numeric store front per country that no answer echoes, so a wrong country cannot be caught), and Google Play search (its robots.txt asks programs to stay out of `/store/search`). A Google Play app gets the screen's empty state, never a rank.
58m. A rank is a `keywordDays` row (Dexie version 3), one per app, country, keyword and UTC day; a later answer the same day replaces it, and rows outlive "Stop tracking" and "Remove the data" (`clearApp` keeps every `keywords:` key too), since no store keeps past ranks. Lists and the newest search per keyword and country live in meta. The background pass (`useKeywordWatch`, main window only, a minute after start and every 30 minutes) and opening the screen fill only the searches with no row for today (`searchesDue`), so a day with every row asks Apple nothing; Check now asks again but reuses a search under an hour old (`freshSearch`), which Apple's CDN would answer from the same copy anyway. One check runs per browser (`osg-growth-keyword-check`), and three failures in a row end it, with `trouble` asking the pass to wait an hour. A day without a check says nothing: a move compares only with a reading inside its window (`MOVE_WINDOWS`: 1 to 3, 7 to 10, 30 to 37 days before the latest), and the screen names that reading's day; misses are counted in checks (`notFoundChecks`), never in days, and the Store page's not-found tip also needs a reading under `STALE_AFTER_DAYS` old. Today's rows take the apps followed since they were written from the very search they came from (`fillRivalRanks`, same `at`), in a transaction that reads each row again (`updateKeywordDays`), so a newer row a check wrote is never undone; an app with no value in a row was not checked, which the screen never shows as not found.
58n. The app ranked is the Growth app when its id is an App Store id, else the App Store app named as the user's on Competitors' `''` list (`keywordAppOf`), so the web build and a desktop with no key rank the same app Competitors compares. The Store page tie-in only ever writes listing drafts (rule 54): its two checks are tips (tracking words for research must not raise the Store page's badge), worked out on the listing with the waiting changes applied (`withChanges`), so a Fix adds to an edit instead of undoing it, and Add every fix adds them after the other fixes. Tell them from the page's own checks on the keywords field with `isKeywordsIssue`, never by the `:keywords:` in an id, which every check on that field has. A result that can land after the country on screen changes (an idea's Check) is kept under `${country}|${term}`, never under the keyword alone. The AI's ideas (`suggestKeywordIdeas`) are words only; every rank on screen comes from a search, never from the AI. The agents read ranks through `list_store_keywords`, and `get_store_overview` and Ask AI get a few lines of them (`keywordDigest`); both read only what the checks stored and never search Apple, so an agent loop cannot spend the 20 searches a minute the checks share, and an app with no value in a row stays absent there too, never null.
58o. Popularity is Apple Ads' search term popularity (`POST /v1/insights/apps/search-term-popularity/query` on api.ads.apple.com; [popularity.ts](../src/lib/growth/popularity.ts) builds the query and reads the rows, [appleAds.ts](../src/lib/growth/appleAds.ts) signs in). It keeps `searchPopularity1to100` (100 is the most searched term in the country, across genres) and `searchPopularity1to5`, one point per term and week (Sunday to Saturday, UTC), the highest of a term's genre rows. A point is named by the Sunday its week starts on, while Apple names the week by the Sunday after it (the `week` field's description, and the endpoint's own example, where Jan 5 to 11, 2025 comes back as `2025-01-12`), so `readPopularityRows` moves it back 7 days; nothing else may. Desktop only: the token trade at appleid.apple.com answers no web page (its OPTIONS answer had no Access-Control-Allow-Origin on 2026-11-15), so the web build shows the prompt and Setup's panel with `Popularity needs the desktop app` and asks nothing. Signing in is a client secret (`createAppleAdsClientSecret`, ES256, `aud` https://appleid.apple.com) traded for an hour's access token, and every API call carries `X-AP-Context: adAccountId=`. The key is a P-256 pair the app makes (`generateEcKeyPair`) or an OpenSSL "EC PRIVATE KEY" (`sec1ToPkcs8`, then rule 57's retry for WebKit). It is kept as `draft` from the first click, so a closed dialog loses nothing, and saved as `key` with an `account` only after `testAppleAdsKey` got a token and the ad accounts (`GET /v1/acls`). Closing the dialog drops a connection still waiting for that answer (`attempt`), and a setup changed meanwhile in another window is never overwritten, so a late answer cannot undo a Disconnect. A window can miss another window's storage event, so every check or save made after a wait (for Apple, or for the database) reads localStorage again (`freshAppleAdsSetup`, `appleAdsSetupStamp`), never the copy in memory, and `setAppleAdsSetup` merges onto what is stored; a refresh reads its key the same way. The dialog's form remembers the private key it is for (`formKey`), which only the dialog moves: opening, Make a key, I have a key already, a successful Connect, Show that key. When the key in hand, the key its IDs were filled from, or the key its ad accounts were listed for (`appleAdsKeyStamp`) is not that one, another window made, connected or removed a key: step 3 says so with Show that key or Start again instead of Connect, and both Connect and an account pick reread storage first and do nothing for a form that no longer fits, so one key is never paired with another key's IDs or accounts. A pick saves only when it is the newest pick and the stored setup is still the one it started from. IDs the dialog filled from a key are filled again from the saved key each time it opens; IDs typed there stay. The connect dialog belongs to the screen, never to the prompt that opens it: the prompt goes the moment Apple Ads is connected, and the dialog has to stay to say so. A record per term and country lives in meta (`keywords:popularity:<country>:<term>`), and its points are empty when Apple sent no row for the term. Apple's documentation says the endpoint returns the most popular terms, and only terms with at least 500 searches and 10 ad impressions in the period, so the screens say "No score", never "not searched", and call the score a comparison between words, never a number of searches or people. A record younger than `POPULARITY_FRESH_MS` (a day) is used as it is, and one request covers a country's due terms (50 at most). A country that got no scores waits as `RETRY_AFTER` says for the kind of error (an hour for a lost connection or a 429, six for the rest), with Apple's words in `keywords:popularity-status:<country>`, which the table shows; Check now asks again at once (`retryRefused`), and a new key or ad account clears every status before it is saved, since saving starts the screens' refreshes. A refresh reads the key inside the Web Lock and stops writing the moment the key or ad account changes (`unchanged`), so a removed or replaced key leaves no records or statuses behind. The screens' refreshes pass `wait`, so the table's and the ideas' (which run in the same render, the ideas' first) never skip each other; only the background pass skips. Apple documents how long it keeps scores (65 weeks, 15 months) and a page size of 5,000 at most, but no limit on a request's range, so a 400 tries 4 weeks and then months (`fetchPopularity`, with `granularity` kept so the screens say months), while a key, role or account error stops the whole refresh. An answer without `result.rows` (or an account list without `result.acls`) is an error, never "no score" for every term. The map's horizontal axis is the fewest ratings in the first ten apps, the user's own left out (`competitionOf`, which Search results' sentence uses too), at log10(1 + n), and its dashed line is the user's own count, so left of the line means Within reach (`chanceOf`). The user's own count has one rule everywhere (`ownFor`): the count a search shows for the app when it lists it, else `ownCount`, the first tracked search in that country that lists the app, else Growth's stored count. So a stored count, which can be days older than a search, decides a chance only when no search on screen lists the app. A keyword is on the map, and Search results states the fewest ratings, only when every other app in the first ten shows a count (`everyCountShown`), since an app with none could have fewer; the map lists the rest under it. For the same reason `chanceOf` says Crowded only for ten other apps that all show more ratings than the user's: a shorter list has room, and an uncounted app could be weaker, so both stay unknown, with no label. A rank not checked yet draws as a dashed hollow dot, never as Not found, and a search whose first ten show no other rating count is listed under the map, never as waiting for a check. They sort `byBestChance` only with popularity on, and hold their order while Check all runs (`frozen`), so no row jumps away from the pointer. Check all's count and Stop stay until its last search answers: with one idea left, with or without popularity, and on another Ideas tab, even an empty one. The agents get popularity in `list_store_keywords`, read from what is stored, never from Apple.

**Capture (simulators and emulators)**

59. Rust runs only fixed `xcrun simctl` and `adb` subcommands ([device_capture.rs](../src-tauri/src/device_capture.rs)), never a shell string on this computer, and every value from the page is checked against a pattern first. Anything that goes through `adb shell` is also quoted for the device's own shell (`device_quote`): adb joins its arguments into one line, and the device's shell reads it. The commands answer editor windows only (`main`, `editor-*`). Two things change a device and are put back: the tidy status bar on quit (`stop_all`, from the run loop's Exit and the updater's `stop_agents`), with the `sysui_demo_allowed` the device had before (`Tidied`, written back after the exit broadcast, because SystemUI ignores a demo command it is no longer allowed to take; noted by `remember_tidy` before the tidy runs, because a tidy cut short by an emulator closing has already turned it on), and a recording when the window that started it closes or loads a page (`discard_recording`, on a thread `stop_all` waits for: the process ending mid-way left the file on the device). An Android device is running only once `sys.boot_completed` is 1: adb answers an emulator half a minute earlier, and a tidy sent then fails with "Can't find service". Stop waits until the encoder goes idle (`wait_for_encoder`: the CPU time of `screenrecord` and `media.swcodec`) before the interrupt, because an emulator's software encoder runs seconds behind a changing screen and screenrecord drops what it has not encoded. The size of the device file says nothing: the muxer holds the frames in memory until the end. `abs_capture_record_start` holds one lock from the "already recording" check to the insert, so two starts for one device cannot both spawn a recorder and leave one that nothing tracks. A stopped or dropped recording stays in the table as `Slot::Saving` until its save ends (`Release`, freed on drop, panics included), because Android's cleanup stops every `screenrecord` on the device and deletes the one shared file; a start in the meantime is refused, not overlapped.
60. A capture goes into the project through `placeShots` or `placeClip` ([place.ts](../src/lib/capture/place.ts)), on the base document and through `handleArtboardsUpdate`. `screenshotSrc` and `mediaId` are always per language, so a capture for German writes German's override and nothing else; in the base language it is written the way Upload Screenshot writes it (the picture's size, a full screen rect), so it also shows in every language without a screenshot of its own. A recording for another language writes its size, length, trims and sound into that language's override and marks each one detached (`keepInLanguage`), even a value equal to the base one today, because `autoDetach` keeps only keys that changed and the language would take the next base clip's length and trim. A cleared trim is written as `null`: a detached key left undefined falls back to the base value. A language the project lacks is refused before `unprojectArtboards`, which hands the edited view back as the document for an unknown language, so the base screenshot would change. `captureScreen`, how Capture reaches a frame's screen, is the same in every language and is written on the base element only.
61. On iOS a screen's link travels with the launch, as the argument `-OSGLink` for the app to open itself, never through `simctl openurl`: iOS asks "Open in <app>?" before it opens any link simctl sends, cold or warm (iOS 26.5, November 2026), nothing can tap Open, and the screenshot came out of the question. Android opens the link with a VIEW intent aimed at the app, which asks nothing.
62. The grid draws small copies of the pictures (`useThumbnail`, [thumbnails.ts](../src/lib/capture/thumbnails.ts)), never the captures themselves: 1320x2868 PNGs drawn into 96px cells came out with a black band across the middle in WKWebView, and each one decoded at full size holds about 15 MB.
63. Playwright's WebKit cannot store the screenshot Blob in IndexedDB (see [tests/e2e/README.md](../tests/e2e/README.md)), so the specs that take one skip on `desktop` behind a probe and run on `desktop-chromium`. The test runtime draws the screenshots itself (`abs_capture_screenshot` in [tauri-runtime.ts](../tests/e2e/fixtures/tauri-runtime.ts)).
64. Every capture commits after seconds of waiting on a device, so it builds on the newest document (`artboardsRef`) and commits through `handleArtboardsUpdateRef`. `placeCapturedScreenshot` runs on the api the `capture_screenshot` call started with, whose own `artboards` would undo every edit made while the app opened and settled. Each capture also checks that the project it started in is still the open one: a copied project has the same frame ids, so finding the frame proves nothing. A recording that stops in another project goes into its own project's tab through `editProjectAnywhere`, and Stop stays on screen whatever the grid or the open project shows.
65. Capture never picks a phone by itself (`bestRunningDevice` with `phones: false`): not on opening, not when the picked device drops out, not for the Properties shortcut, not for `capture_screenshot` without a device id. A phone is someone's phone, and a tidy changes its status bar. A picked device that drops out of one listing stays picked (`seenRef`), not answering, or off under its AVD when an emulator stopped; a failed `adb devices` is an `error`, never an empty list. The listing keeps what each adb serial was called while the serial stays listed (`android_names`): an emulator that is shutting down stays in adb's list for a moment as "device" with its shell closed, then "offline", and without that name the page can no longer tell which AVD to offer Start for. A device whose `getprop` fails is not answering, never running. An iPhone frame never takes another platform's screen (`otherPlatform: false`), and on a computer without the iPhone Simulator its Properties button is off (`iosMissing`).

**Translation**

66. Our LibreTranslate server is one instance for every user and takes 20 requests a minute, so it translates only for a user with no AI of their own set up, and it is never a fallback for one who has: `availableEngines` leaves it out of the list then. The order is in [engines.ts](../src/lib/i18n/engines.ts): Claude Code, then Codex (one-shot prompts on whatever the user signed them in with, which bills their plan or, for a login with an API key, that key; desktop), then the AI panel's provider. Every path that translates takes its engines from `resolveEngines()` and runs through `runTranslation` in [translateRun.ts](../src/lib/i18n/translateRun.ts), which runs languages side by side within each engine's `engineLimits` (three at once for a CLI or an API key, one for the server) and hands what a failing engine left to the next one. The old in-place Translate dialog does too when the user has an AI of their own, and then asks the server nothing, `/detect` included; for a user with none it still calls [translation.ts](../src/services/translation.ts) per element as it always did (`handleTranslateProject`, `handleTranslateElement`), so a change to how the server is used has to touch those two as well as `availableEngines`. A new way to translate goes through `resolveEngines()` and `runTranslation`, never straight to translation.ts. One-shot CLI prompts from a window queue for the CLI's three slots in [agentPrompt.ts](../src/lib/ai/agentPrompt.ts), since Rust refuses a fourth, and Growth's writing jobs share them. Whatever looks for Claude Code or Codex notes the answer in that file's cache (`knownAgentWriters`), the Agent panel's store included, or a sign-in the panel saw never reaches translation and Growth.

**Website (the app's own site)**

67. A site belongs to a project and is kept in a Dexie database of its own (`OpenScreenshotGeneratorWebsite`, [website/store.ts](../src/lib/website/store.ts)), never on the `Project` (rule 1 would drop it). Its screenshots are never stored: the view takes them from the canvas each time (`captureBoardsForWebsite` in the layout, the Export dialog's recipe, through `withLocaleOnCanvas`), refused when another project is open by then. The editor is `invisible` behind the view and html-to-image copies every computed style, so each board gets `visibility: visible` for its own capture; without it the PNG is blank, which website.spec.ts checks by counting dark pixels. A waiting site save is written by `flushWebsiteSaves`, which `beforeWindowCloseRef` calls (rule 39a). Work started for one project stays that project's: a publish takes its draft by `projectId`, and `takeShots(locale, projectId)` throws `ProjectChangedError` when the view was given another project at any point during a capture (`projectCount`, counted in render), so the publish stops before GitHub is touched. Comparing the project before and after is not enough: two blank projects share their artboard ids, so A, then B, then A again captured B's canvas as A's. A capture during which the artboards changed comes back with a null `print` and is not cached. Results that end later (AI answers, translations, publish records) go through `changeSite` ([store.ts](../src/lib/website/store.ts)): into the view's copy while it holds that project (on screen or still being read), otherwise read and written in one transaction, so two results landing at once both stay. The view's copy is `SiteCopy`, a plain class React reads through useSyncExternalStore, so a change is in it the moment it is made and a save right after (the window closing) writes it; a change React had only queued was saved without it. A capture gives up after `CAPTURE_TIMEOUT_MS` so one that never ends cannot stall the queue, and Stop ends a publish while a screenshot is still being taken (`unlessStopped`). To hold a capture in a test, patch `FontFaceSet.prototype.ready`, never `document.fonts` itself: WebKit drops a property set on a DOM object when it collects the object's wrapper and makes a new one, so under load the hold vanished and the test passed or failed by timing.
68. The privacy policy is fixed English sentences chosen by the answers ([privacy.ts](../src/lib/website/privacy.ts)), never written by the AI: the chat may change the answers, and a `privacyExtra` it sends is only `ChangeReport.suggested`, which goes in when the developer presses the button under the answer. A sentence promises only what an answer said: no "only for", "never" or "not to find out who you are"; deleting within a month is an answer of its own (`deleteWithinMonth`); "we don't sell your data" goes when ads are personalised; the services named are the only ones that get data, which the questions say, and every kind of data has a box to name its own (a maps or a push service too). Every change the AI sends goes through `applyChanges` ([content.ts](../src/lib/website/content.ts)), field by field: within `LIMITS`, no email address but the support one, no web address but the store links, and a new support email or store link only when the developer wrote that whole address in the chat (`ChangeContext.said`; "support+help@" gives no "help@", and a longer App Store id no shorter one). It is applied to the site as it is when the answer lands, never to the one the prompt was built from, since an answer takes seconds and the fields stay editable. Writing goes through `runAssistantTurn` in growth/ai.ts (rule 51). Undo in the chat shows only while `siteFingerprint` still matches the site right after that answer, so it never throws away an edit made by hand since.
69. Translations are stored by the `hash32` of the text they translate ([strings.ts](../src/lib/website/strings.ts)), so an edited sentence shows in the base language until it is translated again. Two sources: the developer's and the AI's text (in `content.lang`, no source language sent, since it can mix the starting English and the base language) and the fixed words and the policy (English). A screenshot caption takes the project's own translation first (`projectTranslations`). A translation that drops an email or web address of its source is refused (`keepsAddresses`). Every run goes through `resolveEngines()` and `runTranslation` (rule 66).
70. [render.ts](../src/lib/website/render.ts) is pure and draws both the preview and the published files, so the two cannot differ. Links between pages are relative, because a project site lives under `/<repository>/`; every string is escaped, a font family goes through `safeFamily`, and the pages carry one small script and no tracking. The heading face is put on the site as a Google Fonts `text=` subset (`fetchHeadingFace`); loading it from Google would send visitors to Google, which the policy says no one but GitHub Pages sees. The preview frame is not `sandbox`ed, because Playwright's WebKit ran no event listeners in a script-less sandbox, the editor's included; it carries a `script-src 'none'` policy instead, and `document.open()` takes listeners off, so the frame is listened to again after every new page. Below 720px the header puts the page links on a row of their own: German's "Unterstützung" and "Datenschutzerklärung" made one row 43px wider than a 390px phone, and website.spec.ts measures that in the preview. An imported heading font goes on the site only with `theme.shareFont` on, since its license decides.

Publishing ([github.ts](../src/lib/website/github.ts)) uses the account's GitHub sign-in with `public_repo` added (`githubScope`, and the sign-in Worker's `ALLOWED_SCOPES`), or a sign-in kept for the Website view alone when the account is Google Drive, so it never signs anyone out. **Store compliance (the playbook on GitHub)**

72. The playbook is never bundled. [source.ts](../src/lib/storeCompliance/source.ts) names its repository (`RULES_REPO`, the user's fork, branch main), and [sync.ts](../src/lib/storeCompliance/sync.ts) reads it the first time the view shows in a sitting and when it shows six hours after the last check: never at start-up, never on a timer, never in a window that has not opened the view. A check is `GET /repos/.../commits/main` with `Accept: application/vnd.github.sha` and the stored ETag. Signed out, GitHub allows 60 API requests an hour per IP and a 304 counts too (measured 2026-11-17), so nothing may check more often. A new commit brings its `git/trees/<commit>?recursive=1`, and only the core files (`isCorePath`) whose blob hash changed are downloaded, from raw.githubusercontent.com by commit, else jsDelivr by commit, each checked against its git blob hash (`gitBlobSha`); guides (`isGuidePath`) are listed with their hash and downloaded when opened (`readGuide`). Every file kept here matched the git hash GitHub's file list gives for it, guides too (`readGuide` downloads only what the stored list names): when the API does not answer (offline, 403 or 429, with `waitUntil` from GitHub's reset time) or no host sends a matching copy, nothing new is taken. The copy here stays; with none, the view says why and offers Try again. Nothing is ever read from the branch, since the branch has no hash to check against. Real WebKit and Chromium hand GitHub's 304 to the page (measured), but Playwright's WebKit cannot fulfill a 304, so [store-compliance.spec.ts](../tests/e2e/specs/store-compliance.spec.ts) answers WebKit with a 200 of the same commit.
73. An update is one transaction (`RulesStore.commit`), kept only when the commit's two data files parse (`validateRequired`). A broken or missing data file keeps the last copy that worked, says so in the header with the file's path, and that commit is not downloaded again until the branch moves. Only those two files can stop an update: every other core file is optional. One that fails to download keeps its copy here and is fetched at the next check by commit and hash (`fillGaps`, no API request); one that downloads but its screen cannot use (`usableFile` reads each known file as its screen does, so `{"recipes": null}` is as unusable as broken JSON, and a checklist with no boxes as an empty file) keeps the copy that worked and is listed in the catalog as that copy, so it is not fetched again for that commit. Reading is lenient per entry ([parse.ts](../src/lib/storeCompliance/parse.ts)): a rule with no id or title is skipped and an unknown store or level falls back, and the files are stored as text and parsed on read, so a parser fix needs no new download. One check runs at a time across windows (Web Lock `osg-store-compliance-sync`); a window that waited while another checked takes that check (the stored `checkedAt` changed meanwhile) instead of asking again, and every window hears about an update over the `osg-store-compliance` BroadcastChannel. Rules and deadlines new since the last copy are `news`, never on the first copy. The playbook's licence (OpenRoots Agent License 2.3, Section 8.1) asks every copy of it to keep the copyright notice, the licence and the author with it: NOTICE is a core file, so the copy here always holds it, and keep it in `CORE_FILES`. Nothing has to show on screen; the Overview's credits line was taken out at the user's request (2026-11-17).

Ask AI goes through `runRulesPrompt` (growth/ai.ts, the same `runGrowthPrompt`), so the `aiWriter` setting and the AI picker ([AiPicker.tsx](../src/components/open-screenshot-generator/growth/AiPicker.tsx)) are one choice for Growth and Store compliance: one prompt, no tools, and Stop aborts the signal, which ends the CLI. Only a folder picked in Rust's dialog with `book: "prompt"` passes; that list (`PROMPT_BOOK`, prompt-folders.json) is apart from the chats' folders.json, so a chat that lets go of a folder never takes it from a project here, nor the other way round. Codex has no read fence, so it reads no code here, as in the chat, and what Claude Code read reaches no other AI later either: a turn asked with the folder, and any answer Claude Code wrote with such a turn in the conversation, is marked `fromCode` ([chat.ts](../src/lib/storeCompliance/chat.ts) `turnsOf`), and `historyFor` leaves those turns out of a prompt to Codex or the AI panel; `askAboutRules` picks the AI (`rulesPromptGoesToClaude`) in the same tick it sends, and `runRulesPrompt` refuses a `claudeOnly` prompt that would reach another AI. On macOS, Claude Code is judged as the app, and a read in Documents (or the Desktop, Downloads, iCloud Drive, another disk) of a folder the user did not pick in the dialog makes macOS ask and waits, however long: an audit's prompt sat on an unanswered question all night (2026-11-17) because Claude Code reads the folder `PWD` names when it starts, so no CLI the app starts gets `PWD` or `OLDPWD`. A folder picked in the dialog was read with no question, even after a restart (2026-11-18 recheck), but nothing promises that for every folder, so before anything opens a booked folder, `check_folder_access` lists it from a child (`/bin/ls`) and turns a refusal, or a question left unanswered for a minute, into a message that says what to do. Which AI answers is read again whenever the view shows and whenever the window comes to the front (`useRulesAi(active)`), since the AI panel saves a key without telling anyone. A check reads at most `MAX_CHARACTERS` of artboard text ([places.ts](../src/lib/storeCompliance/places.ts)); what does not fit is named on the form and counted in the result (`skipped`), never left out quietly. The AI only points ([ai.ts](../src/lib/storeCompliance/ai.ts)): a finding's rule must be in the playbook and for the user's stores (`checkRules` leaves out web rules, and one-framework rules unless the check reads code), its quote must be in the place it names, or in another place sent, where it moves, or the finding goes; a finding in the code (`place: "code"`) names a file inside the folder and is kept only when `abs_claude_find_quotes` finds its quote there (`verifyCodeFindings`; Rust answers line numbers only and never reads a file the deny rules keep from Claude Code), and a check that reads code keeps the one-framework rules, since the code shows the framework; a bracketed id an answer makes up is cut (`cleanAnswer`); the level, title and fix shown always come from the playbook. The playbook, the screenshots' words and the store page reach the model fenced as data. The checklist is the repository's docs/PRE-SUBMISSION-CHECKLIST.md: `##` sections, groups from `###` or a line of one to three words such as "Apple.", and boxes whose id is the hash of their words, so a box reworded in the repository is a new, unticked box. The playbook is written for developers and lawyers, and the view is for people who are neither, so the repository may carry `data/plain-language.json` ([plain.ts](../src/lib/storeCompliance/plain.ts)): each rule, deadline and checklist box in everyday words, and the checklist's section titles, their intros and its group headings, made and kept in the playbook repository itself (the user's fork): its `scripts/plain-language.py`, run through its `plain-language` skill in `.claude/skills` after every playbook update, writes the file with Claude Code and commits it there; this app only reads it, never bundles or writes it. The file is optional: missing or broken, it costs only the plain words. **Remove background (src/lib/cutout)**

77. The model is never bundled. [models.ts](../src/lib/cutout/models.ts) pins each file to a Hugging Face commit and its SHA-256; [modelStore.ts](../src/lib/cutout/modelStore.ts) downloads it in 8 MB pieces into its own IndexedDB, hashing as it goes ([sha256.ts](../src/lib/cutout/sha256.ts), since WebCrypto only hashes a whole buffer), and refuses a file that does not match. Pieces are ArrayBuffers, never Blobs (Playwright's WebKit), and they exist for memory: one 120 MB buffer copied into a Blob and again for the runtime is most of the 500 MB at which the macOS web view was killed (issue #19). `MODEL_MIRROR_KEY` in localStorage puts another address first (a mirror, the e2e suite); the hash still decides. The worker ([cutoutWorker.ts](../src/lib/cutout/worker/cutoutWorker.ts)) and onnxruntime-web's asyncify WebAssembly are written into `public/cutout/` by [build-cutout.mjs](../scripts/build-cutout.mjs), which `npm run dev` and `npm run build` run first; nothing there is committed, and a change to the worker or anything it imports needs `npm run build:cutout` (`-- --watch` while working on it). One runtime file serves both paths: measured on an M1 Pro, the WebGPU build runs the CPU path at the plain build's speed.
78. Which engine, all measured in November 2026 on 30 DIS5K, 20 PPM-100 and 10 flat-colour pictures (the numbers are in the files): BiRefNet lite at 1024 on WebGPU (0.92 and 0.99 of the right area; 2.1 s a picture in Chromium, 3.6 s in WKWebView), the same weights at 512 on one CPU thread when there is no usable GPU (0.78 and 0.97, 5.9 s; the 1024 model runs out of WebAssembly's 4 GB there), and on a Mac with macOS 14 or later Apple's subject lifting first (0.04 s, nothing to download, 0.39 and 0.93), replaced by the model's mask once that is ready. "Usable GPU" is asked before anything is downloaded (`hasUsableGpu`: `shader-f16` and 8 storage buffers a stage; headless Chromium has no f16 and refused the session after a 118 MB download), and a GPU that still fails to load the model moves the computer to the CPU model for good (`osg.cutout.gpu-failed`). A picture on a plain colour is cut by colour at once with no download (`colorKey.ts`), then fused with the model's mask when the model may be fetched (`fuseWithModel`, 0.88 to 0.98 of the right area on the flat set; its rules and the cases each one fixes are in the file). The model's mask is refined on the full size photo by a guided filter blended in only where the model was unsure (`refineMask`), the one variant that improved every score; edge colours are cleaned with Forte and Pitie's blur fusion (`estimateForeground`). Pictures are worked on at up to 3072 pixels (`WORKING_SIDE`).
79. A library row (`images` in `OpenScreenshotGeneratorLibrary`, [library.ts](../src/lib/cutout/library.ts)) points at media rows: the finished picture is an `asset_` row, so placing it is an `asset:` reference every exporter, bundle and agent already understands, and the photo and mask (`libsrc_`, `libmask_`) are kept so a cut can change later. The row and its media are in two databases, so no transaction holds both: adding writes the media first and the row last, deleting writes the row (its tombstone) first and the media last, and a crash in between leaves an unused media row, never a row whose picture is gone. A changed cut is a new `asset_` id, never new bytes under the old one, so an artboard keeps the picture it was given and a gist never re-sends a file. `placed` is set when a picture goes onto an artboard (a Custom tile, Add to artboard): deleting the row then keeps its picture. A deleted row stays as a tombstone (`deletedAt`) until a sync has told the account. Cuts run one at a time per window ([queue.ts](../src/lib/cutout/queue.ts) `inTurn`, so the worker's two open pictures never mix), with a Web Lock per picture so a second window does not cut the same one, and a picture left `cutting` by a closed window is picked up by the next window that opens the view. Lists draw the row's own small PNG, never the picture (rule 62). The view saves an edit a moment after it is made and loads a picture again only when a cut finishes (`loadedKey`), never on its own save, which would lose the zoom and the undo history.
80. Backup ([backup.ts](../src/lib/cutout/backup.ts)) runs when the user presses it, never on a timer (rule 25a), and merges both ways: only here is sent, only there is fetched, both keeps the later `updatedAt`, a deletion on either side goes on both. Files the merged manifest no longer names are removed, and that list holds every picture either side had, so a new computer pressing it brings pictures down instead of wiping them. Drive keeps a folder at the top of the user's Drive beside the projects' folder, never inside it (every folder there is listed as a project, by installed builds too), with real PNGs and the photos and masks; a gist keeps the finished pictures only, under a tag that does not contain `DESCRIPTION_TAG` for the same reason. Both adapters live in their provider's file (`googleDriveLibrary`, `githubLibrary`) to reuse its helpers.
81. The agents reach the library through `McpDesignApi` methods (`removeBackground`, `listMyImages`, `saveToMyImages`, `deleteMyImage`), implemented with [mcp.ts](../src/lib/cutout/mcp.ts) in the layout, so desktopMcpServer.ts imports nothing new: the CLI lists its tools by loading that module in Node. `remove_background` is in all three `SLOW_TOOLS` lists and counts as a write only with `elementId`. An in-place cut lands seconds after the call began, so it reads the newest document and refuses an element whose picture changed meanwhile, as `placeCapturedScreenshot` does, and keeps the element's frame (no trim) so the subject stays where it was. The tool never waits for a model download (it starts one and says to call again); the Properties panel's button, which is the same path, does wait (`download: true`).
82. Tests: [cutout.spec.ts](../tests/e2e/specs/cutout.spec.ts) refuses every Hugging Face request, so its default run cuts flat-colour pictures, which need no model. `E2E_CUTOUT_MODELS=<folder with birefnet_lite_webgpu_fp16.onnx and model_fp16.onnx>` adds the model's own test, served from the test's server through `MODEL_MIRROR_KEY`: a 120 MB answer through `page.route` closed the browser's session. Playwright's WebKit cannot store the library's Blobs, so the `desktop` project skips behind the Blob probe and `desktop-chromium` runs them. The Rust Vision test (`vision_cuts_a_portrait_out`) runs only with `OSG_VISION_FIXTURE` naming a raw RGBA portrait and its mask (0.973 of the right area in 0.46 s on 2026-11-19).

## Writing comments and user-facing copy

Two skills are mandatory here, not optional polish.

**Any string a user reads**: a toast, dialog, button, tooltip (`title`), `aria-label`, placeholder, settings hint, empty state, start screen or tour card, store listing copy, or an error message that can reach a toast. Load the **`ui-text`** skill ([.claude/skills/ui-text/SKILL.md](../.claude/skills/ui-text/SKILL.md)) **before** writing it. It has the house patterns with real before/after strings, the vocabulary (artboard, project, element, export), and the traps. Then:

- `node .claude/skills/ui-text/copy.mjs locked "<old text>"` before rewording anything. Playwright specs and the `app-screenshots` scripts locate controls by their text, `title` and `aria-label`, so a LOCKED string changes together with its matcher in the same commit.
- `node .claude/skills/ui-text/copy.mjs check` on the diff before you finish.
- Do not sweep old strings. The early toasts in the layout break most of the patterns; fix one only when you are already in that code path.
- Editor copy is hardcoded in components. `src/lib/i18n/` translates the text **inside artboards**, never the editor UI.

**Any code comment or docstring** you write or edit: run it past the **`humanizer`** skill ([.claude/skills/humanizer/SKILL.md](../.claude/skills/humanizer/SKILL.md)). The patterns that come up most in this repo: §30 (writing about the previous version: a comment describes the code as it is, the history goes in the commit), §23 (filler), §1 (inflated claims), §28 (announcing the next point), and §14 (dashes). For UI copy the ones `ui-text` builds on are §4 (sales language), §7 (overused AI words), §13 (passive voice), §14 (dashes), §17 (title case), §19 (curly quotes), §23 (filler) and §24 (qualifiers).

## Adding things

Full recipes with every registration site are in [reference.md](reference.md). The steps people miss:

- **Element type**: type union, renderer, `Artboard.addElement` branch **and** its render branch, `PreviewDialog`, PropertiesPanel, LayersPanel, ElementPalette
- **Template**: the JSON, then its filename in `TEMPLATE_CATEGORIES[].files`. Nothing else discovers it
- **Preview scene** (a whole App Preview board, dropped from the palette's Previews tab): one entry in `PREVIEW_SCENE_LIST` in [previewScenes.ts](../src/lib/previewScenes.ts). That is the only registration site; the tab, the tile and the drop all read it
- **Device**: `DeviceType`, `DEVICE_REGISTRY`, `getFlatDeviceChrome`, `DEVICE_METRICS`, palette tile, MCP `DEVICE_TYPES`
- **3D Studio model** (a real phone the user can turn to any angle): measure it into one `PhoneModel` in `PHONE_MODELS` in [device3dModels.ts](../src/lib/device3dModels.ts). An iPhone comes from Apple's dimensional drawing PDF (its labels plus the drawing's own vector geometry; never estimate a number the drawing gives). Google publishes no drawings, so a Pixel's front comes from its Android Studio device frame in AOSP (drawn at the display's pixel pitch, scaled to the size on Google's spec page; a notch is the cutout path in its AOSP device config) and its back from Google's hardware diagram and Store renders; check it with `check-pixel-frames.js`. A phone that folds sets `fold` (`PhoneFold`) and its model describes it open flat; the iPhone Duo came from Apple's product bezels and tech specs before its drawing was out, and `check-duo-bezels.js` measures it against them. Add its id to `DeviceType`, `DEVICE_REGISTRY` (as `measuredPhone(id)`) and the MCP `DEVICE_TYPES` lists, then run `regen-studio-thumbs.js`. The renderer, box fit, flat chrome and posed metrics all derive from the entry, the palette files it under iPhone or Android by its `maker`, and `tests/unit/device3dStudio.test.ts` checks every model holds together
- **Web AI provider**: `WEB_ADAPTERS`, `PROVIDERS` in `web_session.rs`, extension adapter + manifest + the `build:extension` entry list, `remote.urls` in `capabilities/assistant.json`
- **OpenAI-compatible preset** (a ready-made base URL in the "Use my API key" tab): one entry in `COMPATIBLE_PRESETS` in [providers.ts](../src/lib/ai/providers.ts). That is the only registration site. A preset is a convenience, never a gate: any endpoint works by typing its URL
- **MCP tool**: `McpDesignApi`, the `TOOLS` array, `mcpApi` in the layout (a write commits through `commitForTool`, which reports a refused commit as the tool's error), all three `SLOW_TOOLS` lists if it is slow (desktopMcpServer.ts, mcp_server.rs and the CLI's [session.ts](../cli/src/driver/session.ts)), and `READ_ONLY_TOOLS` in [desktopMcpServer.ts](../src/lib/mcp/desktopMcpServer.ts) if it only reads. The serial runner treats every tool off that list as a write, so a read left off costs each later call a wait of up to 1.5s, and a write put on it loses edits. An argument the editor loads (a picture, a video, a link) needs a name ending in src, source, url or href, because that name is how the code folder guard finds it
- **Font**: `GOOGLE_FONTS`, plus `AGENT_FONTS` and a `<SelectGroup>` in [FontFamilySelect.tsx](../src/components/open-screenshot-generator/FontFamilySelect.tsx) if it is a new script. That one component is every picker. Fonts the **user** imports are separate: Dexie `fonts` table, see [customFonts.ts](../src/services/customFonts.ts)
- **Selection command** (anything acting on several layers at once, like align or group): the maths goes in [elementGeometry.ts](../src/lib/elementGeometry.ts) as a pure function over an element array, the handler in the layout, and the button in the multi-selection branch of [PropertiesPanel.tsx](../src/components/open-screenshot-generator/PropertiesPanel.tsx). Geometry commands commit through `commitView` (`position` and `size` are per-language keys); `groupId` and `groupName` are in `NEVER_DETACHABLE`, so grouping writes the base array through `handleArtboardsUpdate` instead, or it claims to have changed every language. Membership is a tag, not a container: [LayersPanel.tsx](../src/components/open-screenshot-generator/LayersPanel.tsx) draws the folder rows from `buildLayerRows`, and `groupCommandState` is what both panels ask whether Group and Ungroup have work to do. Dropping a row onto a group is one write through `dropLayer`, which moves the layer in the z-order and retags it together, so the line the list drew is the state that lands. The rows carry the drop target as `data-drop-*` attributes because the mouse (HTML5 drag) and the finger ([use-touch-drag.tsx](../src/hooks/use-touch-drag.tsx)) both resolve it from whatever is under the pointer. A command reachable from the panel also needs the `DockIntent` arm, see Panel prop below
- **Panel prop**: the field on `DockData` in [protocol.ts](../src/lib/panels/protocol.ts), the value in the layout's `dockData` memo, the prop in `RightDockPanels`, and, if it is a callback, an arm in the `DockIntent` union plus `dispatch` in [useDockHost](../src/lib/panels/useDockHost.ts) and `handlers` in [useDockClient](../src/lib/panels/useDockClient.ts)
- **App Store creative art placement** (an In-App Event card, say): its id in `CreativeAssetKind` and one entry in `CREATIVE_ASSETS` in [creative/specs.ts](../src/lib/creative/specs.ts), the only registration site: its size and formats from Apple's specification page, its safe area from the "Art Safe Area" layer in Apple's own template, its file tag and its preset id. What an iPhone shows of it is worked out from `IPHONE_WINDOW_ASPECT` in the same file, per placement, so a placement with a window of its own adds one there. Its looks go in `CREATIVE_LOOKS` in [creative/layouts.ts](../src/lib/creative/layouts.ts); the add dialog, the palette's Header tab, canvas guide, check chip, store preview, export names and the MCP presets all read the registry
- **Store slot** (App Store display type, Play image type): `APPLE_DISPLAY_TARGETS` / `PLAY_IMAGE_TARGETS` in [storeTargets.ts](../src/lib/publish/storeTargets.ts), the only registration site. A size Apple lists before App Store Connect has a display type for it (the iPhone Duo's) goes in `APPLE_DISPLAYS_AWAITING_UPLOAD` instead, so publishing and `osg verify` say it has to wait rather than call it wrong; move it across once the display type is published. A new outbound host also needs `capabilities/default.json`
